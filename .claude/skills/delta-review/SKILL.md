# 델타 코드리뷰 — 무엇을 먼저 볼지 정하는 기준

리뷰는 "모든 줄을 읽는 일"이 아니라 **주의를 어디에 배분할지 결정하는 일**이다.
이 스킬은 diff 를 위험축으로 분류해 **읽는 순서**를 만들고, 축마다 이 코드베이스에서 실제로 사고가 나는 질문을 준다.

## 0. 전제 — 기계가 잡는 것은 사람이 다시 보지 않는다

| 기계 게이트 | 이미 차단하는 것 | 리뷰어가 할 일 |
|---|---|---|
| `guard.mjs` | 금액 double/float, `POSTED`·이력 UPDATE, settlement→order import, account 발행, market 밸류에이션, 도메인 setter/@Data, generic IAE | **돌았는지만 확인** |
| ArchUnit | 도메인→어댑터 import, 서비스 간 의존 방향 | 통과 여부만 |
| JaCoCo | LINE 90% / 핵심 도메인 INSTRUCTION 80% | 통과 여부 + 테스트가 *무엇을* 덮었는지 |
| 이벤트 계약 테스트 | 스키마 ↔ 프로듀서 ↔ 컨슈머 **구조** 드리프트 | 구조가 아니라 **의미** 드리프트(§F) |

기계가 이미 차단하는 규칙을 육안으로 재확인하는 것은 리뷰 예산의 낭비다.
리뷰 시간은 **기계로 표현할 수 없는 불변식**(순서·시점·의미·권한 맥락)에 전부 쓴다.

## 1. 60초 트리아지 — `git diff --stat` 만 보고 순서를 정한다

경로 시그널로 등급을 매기고, **P0 파일이 하나라도 있으면 P0 부터 끝까지 본 뒤 P1 로 내려간다**(섞어 읽지 않는다).

| 경로·패턴 시그널 | 등급 | 축 |
|---|---|---|
| `**/domain/**` 중 금액·상태·정책 필드, `ledger/`, `settlement/`, `payout/`, `chargeback/`, `loan/`, `investment/` | **P0** | A 돈·원장 |
| `adapter/out/event/`, `**/outbox/`, `@Transactional` 이 붙은 서비스 메서드 변경 | **P0** | B tx·Outbox 원자성 |
| `adapter/in/kafka/`, `processed_events`, 컨슈머 핸들러 | **P0** | C 멱등·재처리 |
| `*Controller`(sellerId/userId 파라미터), `SecurityConfig`, `/internal/**`, `/admin/**` | **P0** | D 인가·IDOR |
| `db/migration/*.sql` | **P0** | E 마이그레이션 |
| `contracts/events/*.schema.json`, 이벤트 페이로드 DTO | P1 | F 계약 의미 |
| `readmodel/`, `projection`, `settlement_*_view` | P1 | G 프로젝션 정합 |
| `application/port/**`, `application/service/**` | P1 | H 포트 경계 |
| 상태 enum, `canTransitionTo`, `transitionTo` | P1 | I 상태머신 |
| `settings.gradle.kts`, `build.gradle.kts`, gateway 라우트, nginx, Dockerfile, `application.yml` 스캔·JPA 설정 | P1 | J 배선 |
| 그 외(테스트·문서·정적 리소스) | P2 | K 품질 |

**등급 승격 규칙**: P1·P2 파일이라도 *같은 커밋에서 P0 파일과 함께 바뀌었으면* P0 축의 종속 근거로 함께 읽는다
(예: 마이그레이션 + 엔티티 + 컨슈머가 한 델타에 있으면 세 개를 한 묶음으로 판정한다).

## 2. 읽는 순서 — 세로는 안에서 밖으로, 가로는 3자 동시

**세로(한 서비스 안, 헥사고날)**: `domain/` → `application/port/` → `application/service/` → `adapter/`
도메인 불변식 결함은 어댑터 결함보다 회복 비용이 크고, 어댑터의 옳고 그름은 **도메인 계약을 먼저 알아야** 판정된다.
어댑터부터 읽으면 "코드가 하는 일"은 보이지만 "해야 할 일"과 대조할 기준이 없다.

**가로(서비스 간, MSA)**: 프로듀서(`adapter/out/event/`) ↔ 계약(`contracts/events/*.schema.json` + 정본 샘플) ↔ 컨슈머(`adapter/in/kafka/`)를 **동시에 연다**.
한쪽만 보면 통과처럼 보이는 것이 이 아키텍처의 대표 실패 모드다.
→ **델타에 3자 중 일부만 있으면 그 자체가 1순위 지적 후보**다: 누락된 쪽이 (a) 변경 불필요임을 근거로 밝히거나 (b) 함께 바뀌어야 한다.

**프로젝션 경유 경로**(order → Kafka → `settlement_*_view` → settlement 로직)는 위 3자에 **뷰 스키마와 백필**을 더해 4자로 읽는다(ADR 0020).

## 3. P0 축별 점검 질문

### A. 돈·원장
- 라운딩이 **어느 시점**에 일어나는가 — 항목별 라운딩 후 합산 vs 합산 후 라운딩(결과가 다르다). 기존 코드와 같은 시점인가?
- `commission_rate` 같은 **스냅샷 값**을 정책 테이블에서 다시 읽지 않는가(과거 정산이 미래 정책으로 재계산되면 회계 손상).
- 전표가 차1·대1 균형 팩토리를 경유하는가, 금액 부호·역분개 방향이 뒤집히지 않았는가.
- 경계값: 0원, 음수(환불·조정), 부분환불 반복, 홀드백 차감 후 잔액 음수.

### B. 트랜잭션 경계 · Outbox 원자성
- 상태 변경과 `outbox_events` INSERT 가 **같은 트랜잭션**인가(다르면 유실·유령 이벤트).
- 트랜잭션 안에서 외부 HTTP/PG 호출을 하는가(락 보유 시간 → 커넥션 고갈).
- 같은 빈 내부 호출로 `@Transactional` 이 무력화되지 않는가, `REQUIRES_NEW` 의 롤백 범위가 의도대로인가.
- "커밋 후 발행"을 가정한 코드가 커밋 전 상태를 읽지 않는가.

### C. 멱등 · 재처리
- `event_id` 를 **어디서** 만드는가 — 재시도 때 새 UUID 가 생기면 3단 방어 ①이 무력화된다.
- `processed_events (consumer_group, event_id)` 키가 실제 소비 단위와 일치하는가.
- 컨슈머가 **두 번 실행돼도** 안전한가 — 지급·알림·외부 호출 같은 부수효과가 재실행되지 않는가.
- 도메인 UNIQUE(예: `settlements.payment_id`)가 새 경로에도 걸리는가.

### D. 인가 · IDOR
- 셀러/기업 식별자가 요청 파라미터에서 오는가, JWT 주체에서 파생되는가.
- 집행·취소·조회 각각에 소유권 대조가 있는가(조회만 빠지는 경우가 흔하다).
- `/internal/**` 가 gateway 라우트에 노출되지 않는가, `/admin/**` 가 ADMIN 강제 밖으로 새지 않는가.

### E. 마이그레이션
- **과거 버전 파일을 수정**하지 않았는가(신규 `V{timestamp}__` 만).
- NOT NULL·UNIQUE 추가에 기존 행 백필이 선행되는가, 실패 시 배포가 멈추는가.
- 대용량 테이블 인덱스/락 — 무중단 전제인가.
- **배포 순서**: 새 컬럼을 읽는 코드가 마이그레이션보다 먼저 뜨면 깨진다. 롤백 시나리오가 있는가.

## 4. P1 축별 점검 질문

### F. 이벤트 계약 **의미** 드리프트 (스키마 테스트가 못 잡는 영역)
- 추가 필드가 컨슈머에게 optional 인가(구버전 프로듀서가 살아있는 동안 null 이 온다).
- enum 값 추가 시 컨슈머의 default 분기가 있는가(미지의 값에 예외를 던지면 컨슈머가 정지한다).
- **같은 필드명의 의미 변경**(총액→공급가, 세전→세후)은 스키마가 통과시킨다 — 이건 리뷰어만 잡을 수 있다.

### G. 프로젝션 정합
- settlement 로직이 참조하는 필드가 뷰에 **존재**하는가, 이벤트가 그 값을 싣고 있는가.
- 이벤트 **도착 순서·지연**을 가정하지 않는가(payment 가 order 보다 먼저 올 수 있다).
- 뷰에 컬럼이 늘면 **과거 데이터 백필**이 필요하다 — 백필 없이 조회하면 조용히 null 로 계산된다.
- 대사(`/internal/recon`) 결과에 미치는 영향이 검토됐는가.

### H. 포트 경계
- 포트 시그니처에 JPA 엔티티·Spring 타입·어댑터 DTO 가 새지 않는가(ArchUnit 이 패키지 방향은 잡지만 **타입 누출**은 못 잡는 경우가 있다).
- 유스케이스가 어댑터 관심사(페이징 객체, HTTP 상태)를 반환하지 않는가.
- 도메인에 프레임워크 애너테이션·시간(`LocalDateTime.now()`) 직접 호출이 들어가지 않는가(테스트 불가 지점 생성).

### I. 상태머신
- 새 상태/전이가 `canTransitionTo` **전이표**에 반영됐는가(코드 분기만 늘리면 우회 경로가 생긴다).
- DB 제약·기존 행이 새 상태와 호환되는가, **소비측 서비스**의 분기가 새 값을 처리하는가.

### J. 배선 5곳
새 도메인·서비스는 컴파일이 아니라 **런타임에 조용히** 실패한다 — 스캔·JPA·gateway·nginx·Dockerfile.
자세한 체크리스트는 `msa-service-wiring` 스킬.

## 5. P2 — 남은 예산으로

동시성(락 획득 순서·범위) · N+1 과 인덱스 · **테스트 델타**(돈 경로 프로덕션 변경인데 테스트 변경 0이면 지적) ·
로그·메트릭 유무 · 문서 드리프트(휘발성 수치는 문서에 박제하지 말고 재현 명령으로 남긴다).

## 6. 보고 형식

```
[P0] <file:line> <축A~K> — <한 줄 결함> → 실패 시나리오: <입력·상태 → 잘못된 결과>
[P1] ...
[관찰] <근거는 있으나 실패 시나리오를 못 쓴 것>
---
게이트: test / jacoco / archunit / 계약테스트 — 실행 결과 또는 "미실행" 명시
검사 범위: 파일 N개 · 적용 축 M개(적용 안 한 축과 이유 1줄)
델타 밖 기존 결함: <별도 섹션 — 스코프 혼동 금지>
```

규율 3가지:
1. **실패 시나리오를 쓸 수 없으면 지적이 아니다** → `[관찰]` 로 낮춘다.
2. **발견 0건이어도 "검사 범위"를 반드시 출력**한다 — 침묵 통과와 구별되지 않으면 리뷰가 아니다.
3. 델타 밖 기존 코드 결함은 섞지 않고 별도 섹션으로 — 이 PR 의 책임 범위를 흐리지 않는다.

## 7. 깊게 파야 할 때 위임 (선택)

축 A·원장 → 🤖`gl-ledger-auditor` · 축 B/C/F → 🤖`event-contract-reviewer` · 축 D → 🤖`security-auditor` ·
축 H → 🤖`hexagonal-arch-reviewer` · PII/이력/감사 관점 전용 → 📘`compliance-review`(⌘`/compliance-scan`).
도메인 규칙 근거가 필요하면 해당 `{서비스}-rules` 스킬을 근거로 인용한다(리뷰어의 기억이 아니라 문서가 정본).

## 8. 종결

리뷰 통과는 완료가 아니다. 델타를 머지·커밋하기 전에 📘`verify-before-done` 의 게이트 출력을 증거로 붙인다.
같은 컨텍스트에서 작성과 검증을 겸하지 않는다(자기 승인 금지).
