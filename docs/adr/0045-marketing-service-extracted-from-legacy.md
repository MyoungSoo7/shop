## 컨텍스트

레거시 저장소 `ssgb2e-front_20250721`(Spring MVC + JSP + MyBatis + Oracle, 패키지 `kr.co.dodoom`)에
출석체크와 럭키박스 두 기능이 있다. 마케팅 담당자가 캠페인을 열고 회원이 참여해 포인트를 받는,
전형적인 **이벤트 프로모션 운영 도구**다. 이 저장소로 옮기면서 어디에 둘지가 문제였다.

옮기는 과정에서 레거시 코드가 실제로 들고 있던 결함 다섯을 확인했다. 이건 설계 취향이 아니라
이관 대상의 사실이다:

1. **당첨을 기록하지 않고 포인트도 지급하지 않는다.** 럭키박스는 추첨까지만 하고
   `// 당첨아이템 등록` · `// 마일리지인 경우 지급일 확인 후 지급` · `// 마일리지 유효기간
   있는경우 설정` 세 주석 아래가 전부 비어 있다(`EventServiceImpl.java:537-539`). 응답은
   `itemtype=%s, mileage=%s, text=%s` 라는 디버그 문자열이다.
   여기서 수량 확인도 같이 무너진다 — 확인 코드는 **있지만**(`:482` 이하) 소진 판정을
   `TBL_LUCKYBOX_APPLY` 의 `COUNT` 로 하는데 그 테이블에 쓰는 `INSERT` 가 저장소 전체에
   한 문장도 없다. 따라서 "선착순 100명" 은 영원히 0명으로 집계되고, 참여내역 화면도 늘 빈
   목록이다. 출석체크에는 이 구멍이 없다(참여·성공 등록과 마일리지 지급이 모두 이어져 있다).
2. **참여 횟수 제한이 비어 있다.** `// 참여횟수 확인(금액구분/주문상태/주문금액)` 과
   `// 참여횟수 제한` 아래가 비어 있다(`:478`, `:480`).
3. **등록하는 순간 노출된다.** 초안 상태가 없어서 작성 중인 캠페인이 즉시 사용자에게 보인다.
4. **경품 없이도 이벤트가 열린다.** 참여하면 아무 일도 일어나지 않은 채 참여 횟수만 소진된다.
5. **0 포인트 경품이 등록된다.** 사용자에게는 "당첨"으로 보이고 잔액은 그대로다.

> 2026-08-29 정정. 최초 판에는 ① 이 *"수량 확인 코드가 없다 — `// 아이템 수량 확인` 아래가
> 비어 있다"* 로 적혀 있었다. **주석 아래는 비어 있지 않다.** 결론("몇 명에게 나갔는지 확인할
> 방법이 없었다")은 그대로 맞지만 근거가 틀렸고, 그 바람에 더 큰 결함(당첨 미기록·포인트
> 미지급)이 목록에서 빠져 있었다. 대조 전문은 `docs/plan/marketing-legacy-gap.md`.

## 결정

`marketing-service`(8096, DB `lemuel_marketing`)를 **새 모듈로 만든다.** 게이트웨이 경로는
`/api/promotions/**`(회원)와 `/admin/promotions/**`(운영). 포인트 원장은 옮기지 않는다 —
적립은 order-service 안에서만 일어나고, marketing 은 **요청만 한다.**

### ★ 이 결정은 0041~0043 의 방향과 반대다 — 정면으로 적는다

0041~0043 은 서비스를 **줄이는** 사이클이었고(11 → 8), 0043 은 갈 곳 없는 지원 도메인을 위해
`backoffice-service` 를 새로 만드는 안을 *"줄이는 사이클에서 프로세스를 늘리는 모순"* 이라며
기각했다. 이 ADR 은 그 사이클을 깨고 인벤토리를 **8 → 9** 로 올린다.

0037 의 6축으로 정직하게 채점하면 이렇다:

| 축 | 이벤트 프로모션 | 판정 |
|---|---|---|
| ① 정합성 경계 | 참여 기록·경품 수량은 자기 스키마 안에서 닫힌다. 포인트는 애초에 남의 원장이라 여기 없다 | 없음 |
| ② 규제/라이선스 | 없음 | 없음 |
| ③ 장애 격리 | **있음(약)** — 이벤트 트래픽은 오픈 시각에 스파이크가 몰린다. 럭키박스가 죽어도 거래는 무관하고, 반대로 이벤트 스파이크가 주문 경로를 잠식하면 안 된다 | 약하게 있음 |
| ④ 변경/배포 주기 | **있음(약)** — 캠페인은 마케팅 일정에 붙어 코어보다 자주 바뀐다. 다만 이 저장소에 실측 이력이 없다(레거시에서 갓 옮긴 코드다) | 근거 미실측 |
| ⑤ 팀 인지 부하 | 없음 — main 96파일. 한 팀의 일부 크기 | 없음 |
| ⑥ 데이터 오너십 | 있음 — 그러나 0043 이 확인했듯 별도 **스키마**로도 성립한다 | 스키마로 충분 |

**"최소 2축 이상 강하게" 기준을 이 도메인도 넘지 못한다.** 6축만 보면 착지점은
operation-service 의 `marketing` 슬라이스였고, 나는 그 안을 먼저 제안했다.
**사용자가 별도 서비스로 만들 것을 재지시했고, 그 지시에 따랐다.** 근거를 사후에 지어내지 않기
위해 위 표를 그대로 남긴다 — 이 분리의 근거는 6축이 아니라 **운영 주체의 결정**이다.

그 결정을 지지하는 사실이 아주 없지는 않다. 축③④가 약하게나마 걸리는 유일한 흡수 후보가
operation 인데, operation 은 0041·0043 으로 이미 관제·알림·게시판·교육 넷을 지고 있고 0043 스스로
*"게시판 트래픽 폭주가 관제 프로세스의 CPU·커넥션 풀을 잠식할 수 있다"* 를 대가로 적어 뒀다.
오픈 시각에 몰리는 이벤트 트래픽을 그 위에 다섯 번째로 얹는 것은 그 대가를 키운다.
**이것은 신설을 정당화하는 근거가 아니라, 신설이 무모하지는 않다는 정도의 사실이다.**

### 포인트 원장은 order 에 남는다 (이 ADR 의 진짜 설계 결정)

marketing 은 포인트를 **직접 적립하지 않는다.** 원장(`point_lot`·소멸·선입선출 차감)은 order 의
자산이고, 두 곳이 같은 잔액을 쓰면 그 순간 분산 트랜잭션이 생긴다. 대신 왕복 한 바퀴다:

```
marketing ──[Outbox]──▶ lemuel.marketing.reward_requested ──▶ order (적립)
marketing ◀── lemuel.point.granted ◀────────────────────────── order (적립 완료)
        보상 PENDING/REQUESTED ──────────────────────▶ CONFIRMED
```

- 발행은 **Outbox 경유**(ADR 0003) — 참여 기록 저장과 보상 요청이 한 트랜잭션에 든다.
- 정렬키는 `memberRef` 가 아니라 **`rewardId`** 다. 한 회원의 보상들은 서로 순서 의존이 없는데
  회원으로 묶으면 헤비유저 한 명이 파티션 하나를 막는다(head-of-line blocking).
- 적립 멱등키는 `(referenceType, referenceId)` = (보상 출처, 보상 UUID). 같은 짝이 다시 와도
  로트는 하나다. `processed_events` 와 겹쳐 두 겹이다.
- 원장 쪽 출처는 `PointLotOrigin.PROMOTION_REWARD` 를 새로 만들었다. `MANUAL_GRANT` 와 나눈 이유는
  회계가 아니라 **추적**이다 — 둘 다 판촉비 분개를 타지만, "누가 눌렀나"와 "어떤 캠페인이 도나"는
  다른 조사다. 한 값에 뭉치면 그 질문을 원장에 던질 수 없다.

### order-service 가 처음으로 Kafka 컨슈머가 된다

`MarketingRewardConsumer`(그룹 `lemuel-order`)가 **order 최초의 `@KafkaListener`** 다. 여기서
잠복 함정을 하나 못 박았다: order 의 컴포넌트 스캔은 루트가 아니라 열거식이고, 지금은 목록에
`github.lms.lemuel.common` 이 있어 결과적으로 DLT 배선이 잡히지만 그건 우연에 가깝다. 누군가 스캔
목록을 정리하며 common 을 빼면 배선이 사라지고 **그래도 기동은 성공한다** — Spring Kafka 기본
핸들러가 대신 떠서 재시도 소진 메시지를 조용히 skip 한다(사실상 유실). 그래서
`@Import(KafkaConsumerErrorHandlingConfig.class)` 를 명시했다(ADR 0017 의 DLT 규율을 우연이 아니라
선언으로).

### 레거시 결함 다섯은 옮기지 않는다

| 레거시 | 이관본 |
|---|---|
| 당첨 미기록·포인트 미지급 | 추첨과 같은 트랜잭션에서 `LuckyboxDraw` 를 저장하고 `RewardGrant` 를 만든 뒤 outbox 로 `reward_requested` 를 낸다. 그래서 수량 집계가 실제로 오른다 |
| 참여 횟수 제한 없음 | `(campaign_id, member_ref, entry_slot)` 유니크 인덱스. 슬롯 키가 곧 제한 범위다 |
| 수량 확인이 무력 | `tryReserve` — 전체·일일 수량을 WHERE 절에 넣은 **조건부 UPDATE 한 문장**. 갱신 행 0 이면 소진. 읽고-세고-쓰면 마지막 한 개가 두 사람에게 나간다 |
| 등록 즉시 노출 | 등록은 `DRAFT` 로 끝나고 개시는 별도 호출 |
| 경품 없이 개시 | 추첨 가능한 경품이 하나도 없으면 `open` 이 거부 |
| 0 포인트 경품 | 생성자에서 거부(`포인트 경품은 지급 포인트가 1 이상`) |

수정 명령에서 **집계 규칙과 참여 조건을 뺀 것**도 같은 성격이다. `periodType`·`streakRule`·
`entryCondition` 을 도중에 바꾸면 이미 참여한 사람의 진행률과 슬롯 키 의미가 소급해 달라진다
(기간 1회로 참여한 사람이 하루 1회로 바뀌는 순간 다시 참여할 수 있게 된다). 규칙을 바꾸려면
새 캠페인을 연다.

### 화면은 서비스와 같은 커밋에 붙인다

API 만 옮기고 화면을 뒤로 미루면 이 저장소에서는 **부채로 잡히지도 않는다.** 화면-API 대조
게이트(`api-screen-gate`)는 대상 서비스 목록을 손으로 들고 있고, 새 서비스는 그 목록에 없기
때문이다. 즉 "화면 없는 컨트롤러 2개"가 예산(0)을 넘기는 대신 **집계에서 통째로 빠진다** —
게이트가 막으려던 바로 그 상태다. 그래서 신설과 동시에 목록에 넣고, 예산은 0 으로 둔 채
화면 두 개를 같이 만들었다.

| 화면 | 경로 | 부르는 표면 |
|---|---|---|
| 이벤트 (구매자) | `/promotions` | `/api/promotions/**` |
| 이벤트 프로모션 (운영자) | `/admin/system/promotions` | `/admin/promotions/**` |

두 경로가 API 경로와 다르게 생긴 데는 각각 이유가 있다. 구매자 화면은 `promotions` 세그먼트가
nginx 두 벌의 프록시 목록에 **없어서** 그대로 써도 안전하다(`categories`·`orders` 는 목록에 있어
`/browse`·`/order/…` 로 피해 갔다). 운영자 화면이 `/admin/promotions` 가 아닌 것은 SPA 폴백이
`/admin` 하위 중 정해진 네비 그룹만 index.html 로 돌려주기 때문이다 — 그 밖의 경로는 새로고침에서
404 가 되고, 그 사실은 개발 서버에서 드러나지 않는다.

메뉴 행은 order-service 의 `menus` 에 넣는다(`V20260828190000__menu_promotions.sql`). 화면이 부르는
API 는 marketing 것이지만 **메뉴 원장은 한 벌뿐**이다 — 서비스마다 메뉴 테이블을 두면 좌측 네비를
누가 그리는지가 흐려진다.

## 정직한 대가

- **6축 기준을 이 저장소가 처음으로 어긴다.** 0037~0043 이 쌓은 "최소 2축" 규칙은 이 ADR 이후
  **절대 규칙이 아니라 기본값**이다. 다음에 누가 새 서비스를 들고 오면 이 선례를 들 것이다.
  그 인용이 정직하려면 이 문서가 "운영 주체 결정으로 예외를 냈다"고 적혀 있어야 한다 — 그래서
  6축 표를 지우지 않았다.
- **프로세스·DB 컨테이너가 한 벌 늘었다**(8096 + 5441). compose·CI 매트릭스·게이트웨이 라우트·
  이미지 워크플로가 각각 한 줄씩 늘고, 그만큼 운영 표면이 커진다.
- **적립이 비동기가 됐다.** 레거시는 같은 트랜잭션에서 포인트를 꽂았다. 지금은 사용자가 당첨을
  본 시점과 잔액이 오르는 시점 사이에 왕복 한 바퀴(수백 ms~수 초)가 있다. 화면은 `rewardPending`
  으로 그 사이를 표시한다. Kafka 가 멈추면 보상은 `REQUESTED` 로 남고 잔액은 오르지 않는다 —
  유실은 아니지만 **지연은 사용자에게 보인다.**
- **되돌리는 길은 살아 있다.** 슬라이스 경계(도메인/애플리케이션/어댑터)와 스키마가 그대로라,
  operation 으로 접어 넣는 것은 모듈 이동 + 라우트 합류로 성립한다. 외부 계약(REST 경로·토픽명·
  페이로드)은 그 경우에도 불변이다.

## 대안 (기각)

- **operation-service 의 `marketing` 슬라이스** — 6축 기준으로는 이쪽이 정답이었고 내가 먼저
  제안했다. 운영 주체의 재지시로 기각. 되돌릴 때의 착지점으로 남겨 둔다.
- **order-service 흡수** — 포인트 원장과 같은 프로세스라 적립이 로컬 트랜잭션이 된다는 이점이
  있지만, order 는 0041·0042 가 이미 "인지 부하 한계 초과"로 판정한 코어다. 캠페인 트래픽의
  blast radius 를 결제·주문에 싣는 것은 축③을 정면으로 해친다.
- **레거시 그대로 이식(포인트 직접 UPDATE)** — 두 서비스가 같은 잔액을 쓰는 순간 분산 트랜잭션이
  생기고, 원장의 선입선출·소멸 규칙이 두 곳에 복제된다. 기각.
- **동기 REST 로 적립 요청** — 왕복 지연은 같고 장애 전파만 늘어난다(order 가 느려지면 당첨 화면이
  막힌다). Outbox + 이벤트가 이 저장소의 기존 규율(README: 서비스 간 연계는 Kafka 이벤트로만)이다.
