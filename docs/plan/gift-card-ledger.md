# 기프트카드 원장 설계 — 남은 두 번째 구멍 닫기

> 대상: `order-service` 내 `giftcard/` 도메인 + `account-service` GL 매핑 확장
> 관련: [`point-ledger.md`](./point-ledger.md)(먼저 읽을 것 — 여기서는 **다른 점만** 적는다),
> ADR 0024(이벤트 계약), ADR 0035(토픽 카탈로그), `money-safety`·`ledger-invariants` 스킬
> 상태: **설계 + Phase 1 구현 완료**(2026-08-18)

---

## 1. 문제 정의

포인트 원장을 닫으면서 `GIFT_CARD` 텐더는 같은 구멍으로 남겨 두었고, 그 사실을 코드와
테스트로 드러내 두었다.

```java
// CreateSplitPaymentService.java — 포인트 원장 작업에서 남긴 자리
} else {
    // GIFT_CARD 는 아직 원장이 없다 — 포인트와 같은 구멍이 남아 있다는 사실을
    // 코드에 드러내 둔다(docs/plan/point-ledger.md).
    log.warn("원장 없는 내부잔액 tender 통과: type={}, amount={}", ...);
}
```

즉 지금도 **상품권 텐더로는 임의 금액이 검증 없이 통과한다.** 이 문서가 그 구멍을 닫는다.

---

## 2. 포인트와 무엇이 다른가 — 이 설계의 전부

원장 패턴(append-only 엔트리, 자연키 L3 멱등, BigDecimal, 만료 배치)은 포인트와 같다.
**다른 것만 적는다.**

| 축 | 포인트 | 기프트카드 | 그래서 |
| --- | --- | --- | --- |
| 잔액이 붙는 곳 | 계정(요약) + 로트(상세) | **증서(카드) 하나** | 요약 테이블을 두지 않는다(§3) |
| 식별 | userId | **코드**(비밀) | 해시 저장 + 무차별 대입 방어(§5) |
| 귀속 시점 | 계정은 항상 있다 | **등록해야 생긴다** | 발행 → 등록 상태머신(§4) |
| 단위 | 임의 금액 | **권면가** 단위로 발행 | 발행은 권면가, 사용은 부분 허용(§4) |
| 회계 | 부채 + 판촉비 | 부채 + 판촉비(**별도 계정**) | 상품권 부채를 포인트와 섞으면 분리 표시가 불가능(§6) |

### 채택하지 않은 안 — 포인트 로트 재사용

`PointLot.origin` 에 `GIFT_CARD` 를 하나 더 넣으면 사용·환불·소멸 경로를 전부 재사용할 수
있었다. **하지 않는다.** 잔액이 한 풀에 섞이면 "포인트 잔액"과 "상품권 잔액"을 나눠 보여
줄 수 없고, 회계에서도 두 부채가 한 계정에 뭉친다. 화면과 시산표가 요구하는 분리를
원장이 처음부터 지켜야 한다.

---

## 3. 잔액 요약 테이블을 두지 않는 이유

포인트는 `point_accounts`(요약)와 `point_lots`(상세)를 둘 다 두었고, 그래서
**"요약과 상세가 어긋날 수 있다"는 4번째 불변식**이 필요했다.

기프트카드는 요약을 저장하지 않는다. 잔액은 언제나 `Σ(등록된 ACTIVE 카드의 remaining)`
으로 계산한다. 그러면:

- 어긋날 대상이 없으므로 그 종류의 데이터 손상이 **구조적으로 불가능**하다.
- 불변식이 카드 하나로 닫힌다: `0 ≤ remaining ≤ face_amount`.
- 비용은 잔액 조회가 O(보유 카드 수)라는 것뿐인데, 상품권은 주문마다 쌓이는 포인트 로트와
  달리 1인당 수십 장을 넘지 않는다.

동시성은 계정 락 대신 **카드 행 락**으로 잡는다. 여러 장을 걸쳐 쓸 때는 카드 id 오름차순으로
잠가 교착을 피한다.

## 4. 상태머신과 정책 결정

```
ISSUED ──활성화(판매·배포 확정)──▶ ACTIVE ──등록(사용자 귀속)──▶ REGISTERED
                                     │                             │
                                     │                             ├─사용(부분)─▶ REGISTERED
                                     │                             ├─전액 소진──▶ USED_UP
                                     ├─유효기간 경과─────────────────┴─────────▶ EXPIRED
                                     └─분실·부정───────────────────────────────▶ SUSPENDED
```

결정한 것:

- **부분 사용을 허용한다(잔액 이월).** 권면가 단위 강제는 5만원권으로 3만원 주문을 결제할 수
  없게 만들고, 결제 텐더가 이미 부분 금액을 받는 구조와 충돌한다. 지류 상품권의 "60% 이상
  사용 시 잔액 환급" 규정은 온라인 잔액관리형에는 적용되지 않는다.
- **등록은 1회뿐이다.** 이미 등록된 카드는 다른 사용자가 다시 등록할 수 없다 — 그러지 않으면
  코드를 아는 사람이 남의 잔액을 가져갈 수 있다.
- **Phase 1 은 무상(프로모션) 발행만 다룬다.** 유상 판매는 이 저장소에 판매 흐름 자체가 없고,
  판매 시점 부채 인식을 하려면 활성화 시점에 귀속 주체가 필요한데 무기명 상품권에는 그게 없다.
  Phase 1 은 **등록 시점에 판촉비로 부채를 인식**한다(§6) — 회사가 비용으로 준 것이기 때문이다.
- **소멸은 카드 단위**다. 만료된 카드의 잔액 전부가 한 번에 소멸한다.

## 5. 코드 보안

코드는 그 자체가 재산이다.

- **평문 저장 금지.** `code_hash`(SHA-256, UNIQUE)만 저장하고, 화면 표시는 `code_last4` 로 한다.
  코드는 발행 응답에서 <b>한 번만</b> 돌려주며 이후 어디에서도 다시 조회할 수 없다.
- **엔트로피**: `GC-` + Crockford Base32 16자 ≈ 80비트. 사전 공격이 성립하지 않으므로
  솔트 없이 SHA-256 으로 충분하다(솔트를 쓰면 조회를 위해 전수 비교를 해야 한다).
- **무차별 대입 방어**: 등록 엔드포인트에 기존 `RateLimitFilter` 정책을 추가한다
  (`giftcard-redeem`, 사용자·IP 기준). 이게 없으면 코드 공간이 넓어도 봇이 계속 두드린다.
- 실패한 등록 시도는 코드를 로그에 남기지 않는다 — 로그가 곧 코드 유출 경로가 된다.

## 6. 회계 매핑

신설 계정 3종(포인트 계정을 재사용하지 않는다 — 이름이 `POINT_` 접두라 부정확하고, 무엇보다
두 부채를 시산표에서 분리해야 한다):

| 계정 | 방향 | 성격 |
| --- | --- | --- |
| `GIFT_CARD_LIABILITY` | CREDIT | 미사용 상품권 잔액 — 회사가 진 빚 |
| `GIFT_CARD_PROMOTION_EXPENSE` | DEBIT | 무상 발행분의 상대계정 |
| `GIFT_CARD_BREAKAGE_INCOME` | CREDIT | 소멸(낙전) 이익 |

| 토픽 | 분개 | 비고 |
| --- | --- | --- |
| `lemuel.giftcard.registered` | DR `GIFT_CARD_PROMOTION_EXPENSE` / CR `GIFT_CARD_LIABILITY` | 부채가 생기는 유일한 지점 |
| `lemuel.giftcard.used` | DR `GIFT_CARD_LIABILITY` / CR `CASH` | 포인트와 같은 상계 논리 |
| `lemuel.giftcard.restored` | DR `CASH` / CR `GIFT_CARD_LIABILITY` | 사용의 대칭 |
| `lemuel.giftcard.expired` | DR `GIFT_CARD_LIABILITY` / CR `GIFT_CARD_BREAKAGE_INCOME` | 소멸이익 |

`used` 의 대변이 현금인 이유는 포인트와 같다 — `settlement.created` 가 주문금액만큼 현금
유입을 전기하는데 상품권 결제분은 그 시점에 현금이 들어오지 않았으므로, 이 전표가 그 가공의
유입을 상계한다.

**발행(ISSUED)·활성화(ACTIVE)에는 전표가 없다.** 아직 아무에게도 가지 않은 코드는 부채가
아니다. 그래서 "활성화됐지만 미등록인 잔액"은 장부 밖에 있으며, 그 규모는 관리자 콘솔의
지표로 감시한다(유상 판매를 도입하는 Phase 2 에서 판매 시점 인식으로 바뀐다).

## 7. 스키마

`V20260818130000__gift_card_ledger.sql` (order-service, opslab).

- `gift_cards` — 증서이자 잔액. `code_hash UNIQUE`, `face_amount`, `remaining_amount`,
  `status`, `owner_user_id`(등록 전 NULL), `expires_at`, `version`.
  CHECK: `0 ≤ remaining ≤ face`, 1원 단위 정수, 등록 상태와 `owner_user_id` 의 정합
  (등록됐으면 소유자가 있어야 하고, 그 반대도 참).
- `gift_card_entries` — append-only. **카드 단위**라 포인트의 배분 상세 테이블이 필요 없다.
  자연키 `UNIQUE(gift_card_id, entry_type, reference_type, reference_id, sequence)`.

시각은 `TIMESTAMPTZ` — 소멸 시각이 고객 재산이 사라지는 순간이라는 이유가 포인트와 같다.

## 8. 결제 연동

포인트와 같은 자리, 같은 규약이다.

| 지점 | 동작 |
| --- | --- |
| `CreateSplitPaymentService.deductInternalTenders` | `GIFT_CARD` 텐더를 카드에서 차감(만료 임박 순) |
| `TenderRefundExecutor.refundTender` | 환불 멱등 키를 참조로 복원 |

복원 대상 카드는 원 사용 엔트리에서 도출한다 — 환불은 낸 사람에게 돌아가야 하므로 호출자가
넘긴 식별자를 믿지 않는다(포인트와 같은 판단).

## 10. Phase 2 착지 — 입금 대기 선점 (2026-08-22)

포인트 선점(`point-ledger.md` §14)의 자매편. 가상계좌·무통장 결제가 입금을 기다리는 동안
상품권을 붙잡아 둔다. 직전까지는 선점 수단이 없어 **입금 대기 결제에 기프트카드를 아예 거절**했고,
그래서 상품권을 가진 고객이 가상계좌로 결제할 수 없었다.

### 포인트를 그대로 베끼지 않은 지점 — 잠긴 금액을 저장하지 않는다

`gift_cards` 에 `locked` 컬럼을 더하는 것이 가장 쉬운 길이었다. **하지 않는다.** §3 에서 요약
테이블을 두지 않기로 한 이유가 "어긋날 대상이 없으므로 그 종류의 데이터 손상이 구조적으로
불가능하다"였는데, `locked` 를 저장하면 **"저장된 값 vs 선점 행의 합"** 이라는 손상 축이 정확히
그 자리에 새로 생긴다. 가용액은 언제나 `remaining − Σ(ACTIVE 선점)` 으로 계산한다.

그 선택의 귀결이 포인트와의 차이 전부다.

| 축 | 포인트 | 기프트카드 |
| --- | --- | --- |
| 잠긴 금액 | `point_accounts.locked` 에 저장 | **저장하지 않음**(계산) |
| 선점 시 잔액 | 가용 → 잠금 이동 | **전혀 움직이지 않음** |
| 해제 시 | 잠금 → 가용 복원 | **상태만 변경**(되돌릴 잔액이 없다) |
| 선점 행 단위 | 참조당 1행(계정이 하나) | **참조 × 카드**(권면가 단위라 여러 장에 걸침) |
| 확정 시 | 로트 FEFO 소비 + `USE` 엔트리 | 카드별 차감 + 카드마다 `USE` 엔트리 |

비용도 정직하게 적는다: 가용액 조회가 카드 수만큼의 선점 합계 질의를 한 번 더 탄다
(`idx_gift_card_holds_active_card` 부분 인덱스로 받는다).

### 즉시 사용 경로도 함께 고쳤다

`UseGiftCardService` 가 선점을 빼지 않고 계산하면 입금 대기 결제가 잠가 둔 잔액을 즉시 결제가
써 버리고, 나중에 그 입금이 도착했을 때 **확정할 잔액이 남아 있지 않다.**
`GiftCardSelector.consume`·`spendableBalance` 를 선점 차감형으로 넓혔다(기존 무인자 오버로드 보존).

### 경합 — 포인트에서 배운 순서를 처음부터

확정·해제는 근거로 **카드 id 만 스칼라로 먼저** 읽고, 카드를 잠근 **뒤에** 선점을 처음 적재한다.
잠금 전에 선점을 읽으면 ① 읽은 시점과 잠금 시점 사이에 다른 트랜잭션이 해소할 수 있고
② 그래서 재조회해도 영속성 컨텍스트의 낡은 인스턴스가 돌아온다. 포인트 선점에서 동시성 IT 가
실제로 잡은 결함이라 여기서는 같은 실수를 반복하지 않았다.

없는 선점 처리는 방향에 따라 반대다 — 확정은 **예외**(안 받은 상품권을 받은 셈 칠 수 없다),
해제는 **경고 후 통과**(막으면 미입금 만료 배치가 함께 멈춰 재고 회수까지 밀린다).
