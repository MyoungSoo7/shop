## 1. 배경과 문제

프로세스 13개(인벤토리 12 서비스 — 폴리글랏 부속 1묶음이 2 프로세스)가 돌아가는데, **무엇이 아픈지 아는 방법이 로그 뿐**이면 장애는 사용자가 먼저 발견한다.
Prometheus·Alertmanager 는 지표와 알림을 주지만, 그것만으로는 두 가지가 빈다.

| 문제               | 구체적 손상                                                                       |
| ------------------ | --------------------------------------------------------------------------------- |
| **알림 폭주**      | 같은 장애가 5분마다 재발화하면 채널이 마비되고, 진짜 새 장애가 묻힌다             |
| **도메인 실패 부재** | "주문 실패율"·"재고 소진"은 인프라 지표가 아니라 **도메인 사건**이라 지표로 안 잡힌다 |
| **이력 소실**      | 알림은 흘러가고, "이 장애가 언제 처음 났고 몇 번 재발했나"가 남지 않는다          |

operation-service 는 알림과 도메인 신호를 **인시던트라는 1급 개체**로 모은다. 핵심 설계 판단은 하나다 —
**중복을 예외가 아니라 병합으로 다룬다.**

| 영역 | 기능 |
|---|---|
| 인시던트 | 생성·병합(refire)·타임라인·자동 해소·상태 전이 |

## 5. 핵심 유스케이스

### UC-1. 같은 장애가 반복 발화한다

1. Alertmanager 가 5분마다 같은 알림(fingerprint 동일)을 보낸다.
2. 첫 수신은 인시던트를 만든다. 이후 수신은 **새 인시던트를 만들지 않고 refire** 로 병합된다.
3. 발생 횟수와 최종 관측 시각이 갱신되고, 타임라인 기록은 억제 간격을 지킨다.
4. `(source, correlationKey)` partial unique index 가 **활성 중복을 DB 에서 최종 차단**한다.

> 중복은 오류가 아니라 정상 입력이다. 그래서 예외로 튕기지 않고 병합으로 흡수한다.

### UC-2. 경보가 심각해진다

1. WARNING 이던 인시던트에 CRITICAL 이 들어온다.
2. 심각도가 **상향만** 반영된다(하향은 무시).
3. 승격은 **억제 없이 즉시** 타임라인에 기록된다 — 놓치면 안 되는 신호이기 때문이다.

### UC-3. 도메인 실패율을 본다

1. 도메인 서비스가 성공 이벤트(`order.created` 등)와 실패 신호(`ops.order.failed` 등)를 발행한다.
2. 컨슈머가 시각을 5분 창 시작으로 내림 정렬해 같은 행에 UPSERT 누적한다.
3. 실패율은 저장하지 않고 **조회 시 `countSignal / countTotal` 로 계산**한다.

### UC-4. Alertmanager 가 재전송 폭주를 일으키지 않는다

1. webhook 처리 중 오류가 나도 **200 을 반환**한다.
2. 5xx 를 주면 Alertmanager 가 재전송을 반복해 상황을 악화시킨다.
3. 대신 실패는 로그·메트릭으로 남긴다.

## 6. 기능 요구사항

| FR | 요구사항 | 강제 지점 |
|---|---|---|
| FR-1 | 인시던트 전이는 상태머신을 통과해야 한다 | `canTransitionTo` + `InvalidIncidentTransitionException` |
| FR-2 | (출처, 상관키) 당 활성 인시던트는 1건이다 | `uq_incident_active` partial unique |
| FR-3 | 중복 발화는 refire 로 병합한다 | `Incident.refire` |
| FR-4 | 심각도는 상향만 반영한다 | `IncidentSeverity` |
| FR-5 | 일반 refire 타임라인은 억제 간격을 지킨다 | `Incident.refire(.., timelineSuppression)` |
| FR-6 | 승격은 억제 없이 기록한다 | 동상 |
| FR-7 | 신호는 5분 창으로 정렬해 누적한다 | `BucketWindow`(UTC epoch floor) |
| FR-8 | 실패율은 읽기 시점 계산한다 | `MetricBucket.failureRate` |
| FR-9 | webhook 은 어떤 경우에도 200 을 반환한다 | webhook 컨트롤러 |
| FR-10 | 신호 적재 실패는 컨슈머를 멈추지 않는다 | catch 후 ack |

## 7. 도메인 규칙 (BR)

| BR | 규칙 | 근거 |
|---|---|---|
| BR-1 | **중복은 병합** — 활성 유일성을 예외가 아니라 refire 로 표현한다 | `Incident` 설계 |
| BR-2 | **상향만 반영** — 심각도 하향은 무시한다. 한 번 심각해진 사건은 스스로 가벼워지지 않는다 | `IncidentSeverity` |
| BR-3 | **억제하되 승격은 예외** — 노이즈를 줄이되 중요한 변화는 놓치지 않는다 | 타임라인 억제 로직 |
| BR-4 | **적재는 누적, 계산은 읽기** — 버킷에 카운트만 쌓고 파생은 조회 시 만든다 | `MetricBucket` |
| BR-5 | **수신은 절대 실패하지 않는다** — 관제가 발신자를 막으면 관제가 장애 원인이 된다 | webhook 200 + fire-and-forget |

## 12. 역산에서 드러난 격차

### G-1. 관제의 관제가 없다

이 서비스가 죽으면 **인시던트 수집이 침묵한다.** `up{job="operation"}` 을 Prometheus 가 스크레이프해
`OperationServiceDown` 알람의 소스로 삼지만, 그 알람도 **Prometheus 가 살아 있어야** 동작한다.
관제 체인의 최상단은 외부 의존이며, 그 지점의 단일 실패는 조용하다.

### G-2. 신호 유실이 설계상 허용된다

컨슈머가 적재 실패를 **삼키고 ack** 한다(BR-5). 브로커에는 성공으로 보이므로 재시도도 DLT 도 없다.
"통계니까 괜찮다"는 판단이지만, **실패율 지표가 실제보다 낮게 보이는 방향**으로 틀어질 수 있다 —
장애 중에 적재가 실패하면 실패 카운트가 빠진다.

### G-3. webhook 이 인증 없이 열려 있다

`permitAll` + 항상 200 이다. 재전송 폭주를 막는 선택이지만, **아무나 인시던트를 만들 수 있다**는 뜻이다.
gateway 미라우팅이라는 네트워크 경계에만 의존하며, 그 경계가 뚫리면 관제 데이터가 오염된다.

### G-4. 이상탐지가 두 곳에 있었다 — ✅ 해소(2026-08-25)

한때 Java(operation)와 Python(settlement-anomaly)에 각각 존재했고, **어느 쪽이 정본이고 판정이
어긋나면 무엇을 믿는지**가 문서에 없었다. `settlement-anomaly-service` 를 제거해(호출자 0)
**정본은 operation 하나로 확정**됐다. 다시 확률 모델을 도입한다면 operation 안의 판정을 대체하는
형태여야지, 두 번째 판정자를 세우는 형태여서는 안 된다.

### G-5. 상관키 규칙이 출처마다 다르다

ANOMALY 경로는 `metric_key`, Alertmanager 경로는 `fingerprint` 를 상관키로 쓴다. 같은 근본 원인이
두 경로로 들어오면 **서로 다른 인시던트 2건**이 된다 — 병합 설계의 사각이다.
