## 1. 배경과 문제

"시스템이 있으면 보통 공지사항·자료실·FAQ·문의 게시판이 있다." 그런데 이 요구는 **게시판 하나**가
아니라 **게시판을 만드는 능력**을 원한다. 관례적으로는 게시판마다 테이블·컨트롤러·화면을 만드는데,
그러면 세 가지가 무너진다.

| 문제 | 구체적 손상 |
| --- | --- |
| **추가 비용이 배포다** | "공지 게시판 하나 더" 요청에 마이그레이션 + 배포 + QA 가 붙는다 |
| **규칙이 복제된다** | 게시판마다 권한·첨부·비밀글 검사를 다시 짜고, 그중 하나는 반드시 빠진다 |
| **화면이 증식한다** | 게시판 N개 = 라우트 N개. 메뉴↔라우트 정합 게이트가 N배로 흔들린다 |

**게시판을 코드가 아니라 데이터로 만든다**는 것이 이 서비스의 답이다. `board_definitions` 1행이
게시판 1개이고, 프론트의 단일 라우트 `/boards/:boardKey` 가 그 정의를 읽어 자기를 바꿔 그린다.

> "CRUD 게시판"과 "이미지 게시판"은 별개 제품이 아니라 **같은 제품의 두 스킨**이다.

## 2. 목표 / 비목표

### 2.1 목표

| # | 목표 | 성공 판단 |
| --- | --- | --- |
| G1 | 관리자가 **배포 없이** 게시판을 만든다 | 관리 화면에서 생성 → 즉시 `/boards/{key}` 접근 가능 |
| G2 | 게시판 정의가 그 게시판 글의 규칙을 **소유**한다 | 정의와 어긋나는 글이 애초에 만들어지지 않는다 |
| G3 | 게시판별로 **누가 읽고 쓰는지**를 다르게 준다 | 공개 공지 / 운영자 전용 내부 게시판이 한 시스템에 공존 |
| G4 | 첨부·이미지를 **안전하게** 받는다 | 확장자 위장·스크립트 문서·경로 조작이 전부 거절된다 |
| G5 | 다른 서비스에 **의존하지 않는다** | Kafka 발행 0 · 소비 0 · cross-DB 조회 0 |

### 2.2 비목표

- **메뉴를 만들지 않는다.** `menus` 는 order-service 소유다. 게시판 생성이 곧 전사 네비게이션 변경이
  되면 테스트로 만든 게시판·오타 난 이름이 즉시 모두에게 노출된다(설계문서 §6).
- **분류 코드를 정의하지 않는다.** 게시판은 order 공통코드 그룹 코드를 문자열로 가리키기만 한다.
- **회원 정보를 갖지 않는다.** 작성자는 JWT 주체 식별자 + 마스킹된 표시명 스냅샷이 전부다.
- **파일 서버가 아니다.** 첨부는 게시글의 부속이고 상한(20MB)이 있다.
- **워크플로가 없다.** 승인·게시 예약·다국어는 범위 밖이다.

## 4. 제품 범위 — 기능 맵

```
게시판 정의(관리)        게시글                     댓글            첨부
├ 생성/수정/개폐/삭제     ├ 목록(고정→최신, 검색)     ├ 목록          ├ 업로드(내용 판정)
├ 스킨 4종               ├ 상세(조회수)              ├ 작성(답글 1단) ├ 다운로드
├ 접근 역할 4종          ├ 작성/수정/삭제(상태전이)   └ 삭제(자리표시) ├ 삭제
└ 첨부·댓글·비밀글 정책   └ 고정/숨김/복구(운영)                      └ 대표 이미지(목록)
```

## 5. 핵심 유스케이스

### UC-1. 관리자가 게시판을 만들면 화면이 생긴다

관리자가 `/admin/system/boards` 에서 키·이름·스킨·정책을 입력한다 → 정의 1행이 생기고 즉시
`/boards/{key}` 가 열린다. **메뉴 등록은 두 번째 조작**이다("메뉴에 추가" 액션이 order 의
`POST /admin/menus` 를 호출). 만들고 → 확인하고 → 올린다는 순서가 자연스럽게 강제된다.

### UC-2. 사용자가 글을 쓴다

정의의 쓰기 역할을 가진 사용자가 제목·본문을 낸다. 게시판이 HTML 형식이면 **저장 시점에 정화**되고,
비밀글은 게시판이 허용할 때만 가능하다. 작성자는 JWT 에서만 파생되며 표시명은 마스킹 스냅샷이다.

### UC-3. 비밀글은 작성자와 운영자에게만 보인다

목록의 **총건수부터 다르다** — 가시성이 자바 필터가 아니라 질의 조건으로 내려가므로, 남의 비밀글은
페이지에 세어지지도 않는다. 볼 수 없는 글의 상세는 403 이 아니라 **404** 다.

### UC-4. 이미지 게시판에 사진을 올린다

업로드 바이트를 **매직바이트로 판정**해 확장자와 대조한다. 어긋나면 거절, 형식 미상도 거절,
SVG·HTML 계열은 정책이 허용해도 거절. 저장 파일명은 서버가 만든 UUID 다. 목록은 대표 이미지를
한 번의 질의로 채워 그리드로 그린다.

### UC-5. 운영자가 문제 글을 내린다

운영 역할이 글을 숨기면 **작성자에게도** 보이지 않는다(되돌릴 수 있다). 작성자가 지우면 종단이다.
둘을 가르는 이유는 합치면 운영자가 내린 글을 작성자가 되살릴 수 있기 때문이다.

## 12. 역산에서 드러난 격차

### G-1. ~~서버 썸네일이 없다~~ → 해소(Phase 4)

갤러리 그리드가 **원본 이미지를 CSS 로 줄여** 그리고 있었다 — 5MB 사진 20장이 걸린 목록은 100MB 를
내려받는다. 업로드 시 긴 변 400px PNG 축소본을 함께 저장하고 목록은 `/thumbnail` 을 가리키도록 바꿨다.
**축소본을 못 만드는 경우가 정상 경로**다(WEBP·손상 이미지) — 그때는 원본으로 떨어뜨린다.

### G-2. ~~텍스트·CSV 첨부를 받을 수 없다~~ → 해소

매직바이트가 없어 판정기가 인식하지 못했고, 인식 못 한 것은 통과시키지 않는 정책이라 거절됐다 —
자료실 용도에는 실질적 제약이었다. **판정 방법을 따로 만들어** 풀었다: 시그니처가 없으면 내용을
스니핑한다(NUL 없음 · UTF-8 디코딩 성공 · 제어문자 비율 1% 이하). 순서는 시그니처가 먼저다 —
PDF 처럼 앞부분이 아스키인 형식이 텍스트로 잡히지 않게.

"확장자가 .txt 면 통과"로 가지 않은 이유는 그 순간 검사가 사라지기 때문이다. 실측: 바이너리를
`.txt` 로 위장한 파일은 400 으로 거절됐고, CSV·한글 txt 는 통과했다. HTML 을 담은 `.txt` 는
통과하되 `attachment` + `nosniff` + `text/plain` 으로 나가 브라우저가 문서로 열지 못한다 —
**안전은 판정이 아니라 서빙에서 온다**.

### G-3. ~~고아 파일을 청소하는 주체가 없다~~ → 해소(Phase 4)

첨부 삭제는 DB 행을 먼저 지우고 파일을 지운다. 파일 삭제가 실패하면 경고 로그만 남고, DB 기록 실패 시
보상 삭제도 실패할 수 있다 — 하나하나는 드물지만 아무도 치우지 않으면 단조 증가한다.
매일 04:10(KST) 도는 청소 배치를 붙였다. **유예 기간(기본 24시간)이 안전장치**이고, 경계는 남기는
쪽으로 기운다 — 잘못 지운 파일은 되돌릴 수 없다.

### G-4. ~~FAQ·QNA 스킨이 렌더되지 않는다~~ → 해소(Phase 4)

정의는 만들 수 있고 도메인 불변식(QNA ⇒ 댓글 필수)도 강제되는데 프론트가 LIST 로 떨어뜨렸다 —
"만들 수 있는데 그렇게 안 보이는" 상태였다. FAQ 는 아코디언(펼칠 때 본문 지연 로드), QNA 는
답변완료/대기 배지로 구현했다. 배지가 쓰는 `commentCount` 는 페이지 전체를 한 번의 질의로 센다.

### G-5. 게시판↔메뉴 정합을 빌드 시점에 못 막는다 → **격차 아님(의도된 트레이드오프, 수용)**

메뉴는 order DB, 게시판은 board DB 라 FK 로 묶을 수 없다. 관리 화면이 두 API 응답을 **화면에서 대조**해
배지·배너로 알리지만, 이는 런타임 가시성이지 게이트가 아니다.

**이건 고칠 결함이 아니라 선택의 결과다.** 빌드 시점 게이트는 원리적으로 불가능하다 — 게시판도
메뉴도 런타임에 생기는 데이터라 CI 가 대조할 대상이 소스에 없다. 같은 서비스에 있었어도 FK 로
막을 수 있는 건 "고아 메뉴"뿐이고 "메뉴 없는 게시판"은 여전히 못 막는다. 즉 분리 때문이 아니라
**게시판을 데이터로 만든다는 설계**에서 오는 성질이다.

검토한 대안과 기각 사유:

| 안 | 기각 사유 |
| --- | --- |
| order 가 board API 로 주기 검증 | **발행 0·소비 0·cross-DB 0 이라는 이 서비스의 자산을 판다.** 서비스 간 HTTP 결합과 장애 전파 경로가 새로 생긴다 |
| 메뉴를 board 로 옮긴다 | `menus` 는 16개 화면이 공유하는 전사 자원이다. 게시판 하나 때문에 옮길 수 없다 |

**대신 탐지 가시성을 보강했다**: 관리 화면 상단에 "메뉴에 없는 게시판 N개"(활성만) 요약 배너를
추가했다. 행별 배지만 있으면 목록이 길어질 때 놓친다. 닫힌 게시판은 세지 않는다 — 메뉴에서 내리고
닫는 것이 정상 절차라 그때마다 경고가 뜨면 경고가 배경 소음이 된다.

### G-6. ~~정의 변경의 소급 효과가 부분적이다~~ → 해소

첨부 허용을 끄면 데이터·화면·서버가 서로 다르게 반응했다 — 파일은 남는데 화면에서만 사라지고
직링크로는 여전히 받아졌다. **화면을 데이터에 맞추는 쪽**으로 고쳤다(서버를 막으면 이미 배포된
링크가 죽는다): 기존 첨부는 그대로 보이고 '첨부 추가' 버튼만 사라진다. 상세 응답이 첨부를 함께
싣도록 바꿔 화면이 플래그가 아니라 실제 데이터로 렌더를 정하게 했고, 관리 화면에 이 동작을
알리는 안내를 넣었다(설계문서 §16).
